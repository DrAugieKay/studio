
Standard Operating Procedure: Data Security Policy
Version: 1.0
Date: 2024-07-30
______________________________________________________________________

1.0 PURPOSE

This document outlines the data security policies for the FAConLDQ (Financial Advisory Construal Level & Decision Quality) experimental platform. The policy ensures the confidentiality, integrity, and availability of participant data throughout its lifecycle, in compliance with ethical research standards.

2.0 SCOPE

This policy applies to all data collected, stored, processed, and exported by the FAConLDQ platform, including participant responses, derived scores, and system metadata.

3.0 POLICIES

3.1 Access Control

3.1.1 Participant Access: Participants are authenticated anonymously via Firebase Authentication. The Firestore Security Rules strictly enforce that a participant can only read and write data to their own document path (i.e., /experiment_meta/{expId}/participants/{participantId}, where participantId matches their auth UID). Participants have no access to any other participant's data.

3.1.2 Administrator Access: Access to the admin dashboard and raw data is restricted to authorized research personnel. Administrators must be authenticated via Firebase email/password authentication. An 'admin' custom claim on their authentication token grants them read-only access to all participant data for monitoring and analysis, and delete privileges for data management as per the data retention policy.

3.1.3 Firestore Rules: The `firestore.rules` file implements this access control logic. It denies all access by default and explicitly grants permissions based on user ownership or admin status. The rules are designed to prevent unauthorized `list` and `get` operations.

3.2 Data Encryption

3.2.1 Encryption in Transit: All data transferred between the client application and Firebase services is encrypted using TLS (Transport Layer Security) by default.

3.2.2 Encryption at Rest: All data stored in Firestore is automatically encrypted at rest by Google Cloud.

3.2.3 PII Field-Level Encryption: For any fields identified as Personally Identifiable Information (PII), such as open-ended text responses that might contain sensitive information, a field-level encryption strategy will be employed. This involves using a Cloud Function triggered on document write to encrypt the field's content using a key managed by a Key Management Service (KMS) before it is stored. A corresponding function would be used to decrypt the data for authorized analysis only. Note: In the current implementation, free-text fields are redacted during processed export as a primary means of PII protection.

3.3 Data Minimization

The platform is designed to collect only the data necessary to fulfill the research objectives outlined in the study protocol. No direct personal identifiers (e.g., name, email, IP address) are intentionally stored with the session data. Participant IDs are anonymous UIDs generated by Firebase.

4.0 EXPORT WORKFLOW

Data exports are handled through the secure admin dashboard. The "Processed Export" function redacts potentially sensitive free-text fields (e.g., `choice_reason_text`) to prevent inadvertent PII disclosure in shared datasets. The "Raw Audit Log" is for internal validation only and is not for public distribution.

5.0 INCIDENT RESPONSE

Any suspected data breach or security incident must be immediately reported to the Principal Investigator. The incident will be investigated, and appropriate measures will be taken to mitigate the impact, notify affected parties if necessary, and prevent recurrence.

6.0 POLICY REVIEW

This policy will be reviewed annually or in the event of a significant change to the platform architecture or data handling procedures.
